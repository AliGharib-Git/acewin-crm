# ACEWIN

یک CRM عمومی، حرفه‌ای و قابل تنظیم — برای مدیریت مخاطبین، پایپ‌لاین فروش، وظایف و گزارش‌گیری. طراحی‌شده برای اینکه با هر نوع کسب‌وکاری سازگار باشه، نه یک صنعت خاص.

## امکانات

- **مدیریت مخاطبین (Contacts):** ثبت مشتری/سرنخ با وضعیت (Lead/Prospect/Customer/Inactive)، شرکت مرتبط، تگ‌های قابل تنظیم، مالک/مسئول، و جدول زمانی یادداشت‌ها و تعاملات.
- **مدیریت شرکت‌ها (Companies):** هر شرکت با مخاطبین و معاملات مرتبطش، به‌همراه مجموع ارزش پایپ‌لاین باز.
- **پایپ‌لاین فروش (Deals):** بورد Kanban با قابلیت درگ‌ودراپ بین مراحل، مرحله‌های کاملاً قابل تنظیم (از Settings)، احتمال بسته‌شدن، تاریخ تخمینی، و محاسبه خودکار تاریخ بسته‌شدن هنگام رسیدن به مرحله Won/Lost.
- **وظایف و یادآوری (Tasks):** اولویت‌بندی، تاریخ سررسید، ارتباط با مخاطب/معامله، و علامت‌گذاری انجام‌شده.
- **داشبورد گزارش‌گیری:** KPIهای کلیدی، روند درآمد ماهانه، توزیع پایپ‌لاین بر اساس مرحله، و مقایسه معاملات برد/باخت.
- **چند کاربره:** نقش Admin و Member؛ ادمین می‌تونه مراحل پایپ‌لاین، تگ‌ها و اعضای تیم رو مدیریت کنه.
- **احراز هویت:** ثبت‌نام/ورود با JWT. اولین کاربری که ثبت‌نام می‌کنه به‌طور خودکار Admin می‌شه.

## چندسازمانی (Multi-Tenancy)

هر ثبت‌نام یک Organization (تننت) جدید می‌سازه؛ کاربر ثبت‌نام‌کننده ادمین همون سازمان می‌شه. تمام داده‌های CRM (مخاطبین، شرکت‌ها، معاملات، وظایف، KPI، OKR، لاگ‌های AI) به `organization_id` وصل هستن و در سطح سرور (نه فرانت‌اند) فیلتر می‌شن — یک کاربر هرگز نمی‌تونه داده‌ی سازمان دیگه‌ای رو ببینه، حتی از طریق Copilot/AI Action Agent. برای افزودن هم‌تیمی به سازمان از `POST /api/users` (فقط ادمین) استفاده کنید.

## دیتابیس: SQLite (dev) در برابر PostgreSQL (production)

SQLite به‌صورت پیش‌فرض برای توسعه‌ی محلی استفاده می‌شه (بدون نیاز به نصب دیتابیس جداگانه) — در این حالت جدول‌ها هنگام اجرای `uvicorn` خودکار ساخته می‌شن. برای production باید از **PostgreSQL** + **Alembic migrations** استفاده کنید:

```bash
cd backend
pip install -r requirements.txt --break-system-packages

# .env: DATABASE_URL=postgresql://user:password@host:5432/acewin_crm

alembic upgrade head        # اجرای migration ها روی دیتابیس خالی
python seed_demo.py               # (اختیاری) پرکردن با داده نمونه
uvicorn app.main:app --reload
```

دستورات مفید Alembic:

```bash
alembic upgrade head                          # اعمال آخرین migration ها
alembic revision --autogenerate -m "توضیح"    # ساخت migration جدید بر اساس تغییرات models.py
alembic downgrade -1                          # برگشت یک مرحله به عقب
alembic current                               # نمایش نسخه فعلی دیتابیس
```

روی SQLite هم Alembic کار می‌کنه (اختیاریه، چون `create_all` این کار رو خودکار انجام می‌ده)، ولی روی PostgreSQL **قبل از اجرای اپ** حتماً باید `alembic upgrade head` زده بشه — در `main.py` عمداً `create_all` فقط برای SQLite صدا زده می‌شه تا با tracking نسخه‌ی Alembic روی Postgres تداخل نکنه.

سلامت سرویس: `GET /api/health` (زنده بودن پردازش) و `GET /api/ready` (اتصال واقعی به دیتابیس).

## ACEWIN Copilot (لایه ۲) و Analytics Engine (لایه ۳)

علاوه بر CRM Core، پروژه شامل دو لایه هوشمند دیگه هم هست:

### Copilot

دستیار هوشمند زبان طبیعی که فقط از طریق ابزارهای بک‌اند به داده‌های واقعی CRM و تحلیل‌ها دسترسی داره — هیچ‌وقت SQL تولید نمی‌کنه و هیچ داده‌ای رو از خودش نمی‌سازه. برای فعال‌سازی ساده در ایران، از **AvalAI** استفاده کنید. AvalAI یک API سازگار با OpenAI روی `https://api.avalai.ir/v1` دارد؛ کلید API را از داشبورد آن بسازید. اعتبار رایگان یا آزمایشی به وضعیت حساب بستگی دارد.

```
# backend/.env
AI_PROVIDER=avalai
AI_API_KEY=کلید-API-شما
AI_MODEL=gpt-4o-mini
```

نیازی به تنظیم `AI_BASE_URL` نیست؛ برنامه برای `avalai` خودکار از آدرس بالا استفاده می‌کند. بدون تنظیمات AI، Copilot در حالت "architecture-only" کار می‌کنه و توضیح می‌ده که به هیچ مدلی وصل نیست — بدون قطع شدن هیچ بخشی از برنامه.

از داخل اپ، صفحه‌ی «دستیار هوشمند» یک رابط چت‌مانند داره که هر پاسخ رو با ساختار Summary / Analysis / Recommendation / Confidence Score / Business Impact / Next Action نشون می‌ده. با انتخاب فارسی در تنظیمات، درخواست و حالت‌های خطای Copilot هم فارسی می‌شوند.

#### لایهٔ AI Provider (کاملاً مستقل از ارائه‌دهنده)

معماری Copilot هیچ ارائه‌دهندهٔ خاصی رو hardcode نمی‌کنه:

```
AI Provider Interface  →  Provider Adapter  →  ارائه‌دهندهٔ انتخابی  →  LLM
```

انتخاب ارائه‌دهنده فقط با یک متغیر در `backend/.env` مشخص می‌شه (`AI_PROVIDER`) و هیچ تغییری در CRM Core، روتر Copilot، ثبت ابزارها (tools) یا فرانت‌اند لازم نداره. ارائه‌دهنده‌های پیاده‌سازی‌شده:

| `AI_PROVIDER` | ارائه‌دهنده | نکته |
|---|---|---|
| `openai` | OpenAI رسمی | `api.openai.com` |
| `openrouter` | OpenRouter | یک کلید، دسترسی به مدل‌های زیاد از جمله Gemini/Claude |
| `avalai` | AvalAI | سازگار با OpenAI، در دسترس از ایران |
| `gapgpt` | GapGPT | سازگار با OpenAI، در دسترس از ایران، دسترسی به OpenAI/Gemini/Claude |
| `groq` | Groq | inference بسیار سریع روی مدل‌های متن‌باز (Llama و...) |
| `gemini` | Google Gemini | پیاده‌سازی مستقل روی Generative Language API |
| `claude` | Anthropic Claude | پیاده‌سازی مستقل روی Messages API |
| `custom` | هر endpoint سازگار با OpenAI دیگه | نیاز به `AI_BASE_URL` و `AI_MODEL` صریح |
| `none` (پیش‌فرض) | — | حالت architecture-only، بدون تماس شبکه‌ای |

اضافه‌کردن یک ارائه‌دهندهٔ جدید در آینده یعنی فقط نوشتن یک کلاس adapter در `backend/app/ai/client.py` و یک خط در جدول ثبت‌نام آن (`_PROVIDER_REGISTRY`) — بدون تغییر در CRM، روتر یا فرانت‌اند. جزئیات کامل هر ارائه‌دهنده (URL پیش‌فرض، مدل پیش‌فرض) در `backend/.env.example` مستند شده.

#### Action Agent: ابزارهای نوشتنی، مجوز، Audit Log و Undo

علاوه بر گزارش‌گیری، Copilot می‌تونه واقعاً کارها رو هم انجام بده — چون به ابزارهای نوشتنی هم مجهزه:
- **create_task** — ساخت وظیفه، یادآوری تماس یا قرار ملاقات جدید (مثلاً «برای فردا ساعت ۱۰ با امین رضایی یک تماس تنظیم کن»)
- **update_task** — تغییر زمان، اولویت یا وضعیت یک وظیفه (مثلاً «اون تماس رو به‌جای فردا برای پس‌فردا بذار» یا «اون وظیفه رو انجام‌شده علامت بزن»)
- **create_deal** — ساخت معامله جدید در پایپ‌لاین
- **update_deal_stage** — جابه‌جایی یک معامله بین مراحل (مثلاً «اون معامله رو ببر روی برد»)
- **find_contact** — پیدا کردن مخاطب با نام، قبل از ساخت وظیفه/معامله براش

مدل فقط زمانی این ابزارها رو صدا می‌زنه که کاربر صریحاً درخواست ساخت/تغییر/جابه‌جایی چیزی رو داده باشه — نه به‌عنوان عارضهٔ جانبیِ پاسخ به یک سؤال. اگه اسم مخاطب مبهم یا پیدا نشه، مدل موظفه از کاربر بپرسه، نه اینکه حدس بزنه.

هر اقدام نوشتنی — چه از طریق Copilot، چه از طریق REST API — از یک pipeline یکسان عبور می‌کنه:

```
درخواست (UI یا LLM)  →  چک مجوز (RBAC)  →  CRM Service Layer  →  دیتابیس  →  Audit Log
```

- **RBAC یکپارچه** (`backend/app/ai/permissions.py`): یک ماتریس نقش/مجوز مشترک بین REST API و Copilot. نقش `admin` دسترسی کامل داره؛ `member` فقط می‌تونه رکوردهای متعلق به خودش (task/deal/contact) رو ویرایش یا حذف کنه، و عملیات حذفِ سازمانی (شرکت، مخاطب، معامله، تگ) فقط برای admin مجازه — چه از رابط کاربری اقدام بشه چه از Copilot.
- **Audit Log یکپارچه** (مدل `AgentActionLog`، در دسترس با `GET /api/agent-actions`): هر عملیات نوشتنی — چه یک انسان از طریق REST API انجامش داده باشه (`source=api`) چه Copilot از طریق tool-calling (`source=copilot`) — با کاربر، آرگومان‌ها، نتیجه و رکورد مرتبط ثبت می‌شه. تلاش‌های رد‌شده (`denied`) هم ثبت می‌شن. Admin می‌تونه فعالیت همهٔ کاربران رو ببینه؛ بقیه فقط فعالیت خودشون رو.
- **Undo واقعی**: اقدامات Copilot که قابل واگرد هستن (`create_task`, `update_task`, `create_deal`, `update_deal_stage`) یک عکس‌فوری از وضعیت قبلی نگه می‌دارن و می‌تونن با `POST /api/agent-actions/{id}/undo` واگرد بشن — در رابط چت هم دکمهٔ «واگرد» کنار هر tool call نمایش داده می‌شه.

#### KPI Engine (صفحهٔ «شاخص‌ها»)

یک موتور KPI واقعی — نه یک داشبورد با اعداد ثابت. هر عدد در `backend/app/kpi/engine.py` مستقیماً و در لحظه از روی داده‌های واقعی (`Deal`, `Task`) محاسبه می‌شه؛ هیچ عددی cache یا hardcode نشده. شاخص‌های فعلی:

| شاخص | نحوهٔ محاسبه | روند تاریخی |
|---|---|---|
| Revenue Won | مجموع ارزش معاملات برد‌شده در هر ماه | ✓ |
| Win Rate | نسبت برد به (برد+باخت) در هر ماه | ✓ |
| Average Deal Size | میانگین ارزش معاملات برد‌شده در هر ماه | ✓ |
| Sales Cycle Length | میانگین فاصلهٔ زمانی ایجاد تا بستن معاملهٔ برد‌شده | ✓ |
| Task Completion Time | میانگین زمان بین ایجاد و تکمیل وظیفه | ✓ |
| Lead Conversion Rate | از مخاطبین ایجادشده در هر ماه، چند درصد امروز مشتری‌اند (کوهورت) | ✓ |
| Overdue Task Rate | از وظایف با موعد در هر ماه، چند درصد هنوز پس از موعد باز مانده‌اند | ✓ |
| Open Pipeline Value | مجموع ارزش معاملات باز، فقط لحظهٔ حال | فقط snapshot (چون تاریخچهٔ تغییر مرحله ذخیره نمی‌شه، بازسازی روند گذشته صادقانه ممکن نیست) |
| Pipeline Velocity | (تعداد معاملات باز × نرخ برد × میانگین ارزش معامله) ÷ طول چرخهٔ فروش | فقط snapshot (چون تعداد معاملات باز لحظه‌ایه) |

هر شاخص شامل مقدار فعلی، هدف (قابل تنظیم فقط توسط admin، از طریق `PUT /api/kpis/{key}/target` — با audit log)، سطح ریسک (`on_track`/`at_risk`/`critical`، بر اساس نسبت واقعی به هدف — قانون‌محور و شفاف، نه یک مدل جعبه‌سیاه)، و پیش‌بینی دورهٔ بعد (رگرسیون خطی سادهٔ least-squares روی همون داده‌های واقعی، به‌همراه بازهٔ اطمینان تقریبی بر پایهٔ انحراف‌معیار باقیمانده‌ها — با کمتر از ۳ نقطه هیچ پیش‌بینی‌ای انجام نمی‌ده، به‌جای حدس زدن).

برای شاخص‌هایی که روند تاریخی دارن، یک بلوک آمار توصیفی هم محاسبه می‌شه (میانگین، میانه، کمینه، بیشینه، و درصد نوسان نسبت به میانگین) تا معلوم بشه عدد فعلی نسبت به رفتار معمول شاخص کجاست. برای `revenue_won` و `avg_task_completion_hours` یک breakdown هم اضافه شده که ۵ عضو تیم برتر (بر اساس درآمد برد‌شده یا تعداد وظیفهٔ تکمیل‌شده) رو نشون می‌ده. صفحهٔ «شاخص‌ها» این‌ها رو داخل یک بخش «جزئیات» قابل‌باز/بسته‌شدن روی هر کارت نمایش می‌ده، به‌همراه فیلتر بخش (فروش/عملیات)، انتخاب بازهٔ زمانی (۳ تا ۲۴ ماه)، و خروجی CSV از همهٔ شاخص‌های نمایش داده‌شده.

دکمهٔ «توضیح بده» روی هر کارت، از همون لایهٔ AI Provider (فاز ۱) برای تولید یک توضیح کوتاه دربارهٔ چرایی روند، ثبات/نوسان، و اقدام پیشنهادی استفاده می‌کنه — پرامپت فقط شامل همون اعداد واقعیه (بدون داده‌ی جعلی)، و اگر `AI_PROVIDER=none` باشه یا تماس با مدل شکست بخوره، به‌جاش یک توضیح قانون‌محور (rule-based) از همون اعداد نمایش داده می‌شه؛ هیچ‌وقت خطا نمی‌ده.

#### OKR Engine (صفحهٔ «اهداف و نتایج کلیدی»)

```
Objectives  →  Key Results  →  Progress  →  امتیاز بخش  →  امتیاز کل شرکت
```

هر Objective برای یک بخش (`sales`/`operations`/`general`) و یک دورهٔ سه‌ماهه (`period_key` به‌فرمت `YYYY-Q1`..`Q4`) تعریف می‌شه، و شامل چند Key Result است — یا از نوع «عددی» (baseline → target → current) یا «نقطه عطف» (انجام‌شده/نشده). یک Key Result عددی می‌تونه مستقیماً به یک KPI از فاز ۴ متصل بشه (`linked_kpi_key`)؛ در این حالت مقدار فعلی‌اش همیشه زنده از KPI Engine خونده می‌شه، نه از یک عدد دستی که ممکنه قدیمی بشه.

- **امتیازدهی**: امتیاز هر Objective میانگین وزنی امتیاز Key Result هاشه؛ امتیاز هر بخش میانگین Objective های فعال/تکمیل‌شدهٔ اون بخشه؛ امتیاز کل شرکت میانگین امتیاز بخش‌هاست (نه میانگین کل Objective ها — یعنی یک بخش با ۱۰ هدف، بخش دیگه با ۱ هدف رو تحت‌الشعاع قرار نمی‌ده).
- **ریسک، بر اساس زمان، نه فقط عدد**: بر خلاف ریسک KPI (که نسبت عدد فعلی به هدفه)، ریسک OKR بر اساس «پیشرفت مورد انتظار با توجه به گذشت زمان از دوره» محاسبه می‌شه — یعنی یک burn-rate ساده و شفاف، کاملاً قانون‌محور.
- **اولویت‌بندی قطعی**: در `GET /api/okrs/scoreboard`، Objective ها بر اساس شدت ریسک و فاصله از برنامه مرتب می‌شن — یک مرتب‌سازی قطعی، نه یک قضاوت مبهم از مدل.
- **مجوز**: تعریف Objective فقط با admin است (تصمیم رهبری سازمان)؛ مدیریت روزمرهٔ Key Result ها و ثبت پیشرفت با owner همون Objective یا owner مستقیم همون Key Result است.
- **تحلیل هوشمند**: دکمهٔ «تحلیل کن» روی هر Objective، از همون AI Provider Layer برای توضیح «چرا عقب/جلوئیم و چه‌کار کنیم» استفاده می‌کنه — با همون الگوی fallback قانون‌محور در نبود AI Provider.

### Analytics Engine

۱۲ ماژول هوش مصنوعی (Segmentation، Lead Scoring، CLV، Churn، Deal Success، Revenue Forecasting، Sales Trend، Customer Behaviour، Risk Detection، Next Best Action، Business Performance، Executive Insights) که همگی روی دیتاست واقعی **Olist Brazilian E-Commerce** آموزش/اجرا می‌شن، نه داده‌ی ساختگی. فایل‌های CSV این دیتاست داخل `backend/data/olist/` قرار دارن.

اولین باری که این ماژول‌ها اجرا می‌شن (چه از API، چه از Copilot)، محاسبات چند ثانیه طول می‌کشه و نتیجه‌ش توی `backend/data/_cache/*.parquet` کش می‌شه؛ دفعات بعدی سریع‌تره. با `POST /api/analytics/cache/clear` می‌شه کش رو پاک کرد.

صفحه‌ی «تحلیل هوشمند» توی اپ، یک داشبورد از این خروجی‌هاست (Executive Insights، پیش‌بینی درآمد، سگمنت‌بندی مشتری، ریسک ریزش و...). همهٔ خروجی‌های قابل‌نمایش تحلیل، از توضیح مدل و اقدام پیشنهادی تا بخش‌های مشتری، دلایل ریسک و KPIها، با انتخاب زبان فارسی فارسی می‌شوند.

نصب وابستگی‌های تحلیل داده (pandas / scikit-learn / pyarrow) از طریق همون `requirements.txt` انجام می‌شه.
